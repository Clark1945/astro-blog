### HTML

ページを書くための言語です。私の結論は「勉強しなくていい」。いくつかの Web ページを見れば分かります。

```html
<!doctype html>
<html lang="ja">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>ページタイトル</title>
    <link rel="stylesheet" href="css/style.css" />
  </head>
  <body>
    <h1>見出し</h1>
    <p>
      <a href="https://developer.mozilla.org/ja/">リンク</a>を含む段落です。
    </p>
    <script defer src="js/app.js"></script>
  </body>
</html>
```

属性：id、class、data-\*

```html
<article class="event major" id="tw-1895-cession" data-year="1895"></article>
```

- id：ページ内で一意。要素の特定に使い、URL の `#id` アンカーにもなります。
- class：複数付けられ、重複も可。スタイルの適用や要素の選択に使います。

### CSS

HTML が骨格で、CSS がそれを飾ります。
読み込み方は 3 つあります：

- 外部ファイル（`<link rel=...>`、推奨）
- `<style>` ブロック
- 要素の `style="..."`（一時的なデバッグ用のみ）

同じプロパティに複数のルールが当たったときは、詳細度（specificity）が高いほうが勝ちます：インライン style ＞ `#id` ＞ `.class`・属性・疑似クラス ＞ タグ名。同じレベルなら後に書いたほうが勝ちます。`!important` はすべてを上書きできますが、後々のメンテナンスが難しくなるので、なるべく使わないこと。

#### 非同期とブラウザ API

JS はシングルスレッドで動きます。ネットワーク通信やタイマーのように待つ必要がある処理はブラウザに任せ、終わったらコールバックがキューに入り、今のコードが終わってから順番が回ってきます。だから待っている間も画面は固まりませんが、「どれが先に実行されるか」には注意が必要です。

```javascript
<script>
console.log("1");
setTimeout(() => console.log("4"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("2");
// 実行順は 1 2 3 4
</script>
```

Promise と async/await

```javascript
async function loadJson(url) {
  const res = await fetch(url); // ネットワークを待つが、画面は固まらない
  if (!res.ok) throw new Error("HTTP " + res.status); // fetch は 404 でも自分からはエラーを投げない
  return res.json(); // これも Promise
}

async function main() {
  try {
    const data = await loadJson("/data/taiwan.json");
    console.log(data.events.length);
  } catch (err) {
    console.error("読み込み失敗", err);
  }
}
main();
```

```javascript
try {
```

#### HTML の制約検証（Constraint Validation）

| 属性                              | 効果                                             | 注意点                                                                                                       |
| --------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `required`                        | 空欄不可、必須項目。                             | 未入力のままではフォームを送信できない。                                                                     |
| `type="email"`                    | メールアドレスの形式かをチェック。               | スマホではメール入力向けのキーボードが表示される。                                                           |
| `type="url"`                      | URL の形式かをチェック。                         | 通常は `https://` などのスキームが必要。                                                                     |
| `type="number"`                   | 数値のみ入力可。                                 | 電話番号・郵便番号・ID 番号には不向き。先頭の `0` が消えることがある。                                       |
| `type="date"`                     | 日付ピッカーを表示し、日付の形式を検証。         | 値は標準の日付形式で扱われる。                                                                               |
| `type="text" inputmode="numeric"` | テキスト欄だが、スマホでは数字キーボードを表示。 | 先頭の `0` を残したい電話番号・郵便番号・ID 番号に向いている。                                               |
| `pattern`                         | 正規表現で入力形式を検証。                       | 文字列全体が一致する必要がある（暗黙の `^(?:…)$`）。テキスト系の入力のみ。`title` でルールを説明するとよい。 |
| `min` / `max` / `step`            | 数値・日付・範囲の最小値・最大値・刻み幅を設定。 | 主に `number`・`date`・`range` で使う。                                                                      |
| `minlength`                       | 最小文字数を設定。                               | ユーザー名やパスワードでよく使う。                                                                           |
| `maxlength`                       | 最大文字数を設定。                               | 上限を超えて入力できなくなる。                                                                               |

- フロントエンド検証とバックエンド検証：フロントの検証は体験のため（即時フィードバック、往復が一回減る）。バックエンドの検証こそがセキュリティの境界です。誰でも curl でフロントを迂回できるからです。両方やること。Spring Boot なら `@Valid` と Bean Validation（`@NotBlank`、`@Email`、`@Size`）で 400 とフィールドエラーを返し、フロントはそのエラーを各フィールドに対応させます。両者のルールはずれていくので、バックエンドを正とします。
- 二重送信の防止：submit イベントの中で送信ボタンを無効にし、フラグでガードする（Enter キーとボタンは同じ経路を通る）。バックエンドも冪等にしておく（idempotency key やユニークキー）。ユーザーはリロードも連打もできるし、ネットワークのリトライも起きるからです。
- 会員登録・決済・管理画面の CRUD フォームなら、ほとんどのルール（必須・形式・長さ）は属性で足ります。複雑な項目間ルール（パスワード確認、開始日と終了日）だけ `setCustomValidity` を使います。
- 送信には `form.submit()` ではなく `form.requestSubmit()` を使う：前者は検証を実行し submit イベントも発火させますが、後者はどちらも飛ばします。

#### リソースの読み込み

HTML パーサーは「ダウンロードしながら解析する」ストリーム処理です。`<script>` に出会ったときの動きは属性で決まります。選び方を間違えると、「ページが遅い」から「`querySelector` が `null` を返す」まで、いろいろな問題が起きます。

| 読み込み方               | ダウンロード                            | 実行タイミング                               | 複数スクリプトの順序                    | 後ろの DOM が見えるか | 用途                                         |
| ------------------------ | --------------------------------------- | -------------------------------------------- | --------------------------------------- | --------------------- | -------------------------------------------- |
| 普通の `<script>`        | すぐにダウンロードし、HTML 解析を止める | ダウンロード後すぐ実行、解析はブロックされる | 文書順                                  | ❌ 見えない           | ほぼ使うべきでない                           |
| `<script defer>`         | 解析と並行                              | HTML 解析完了後、`DOMContentLoaded` の前     | ✅ 文書順                               | ✅ 見える             | アプリ本体のコード                           |
| `<script async>`         | 解析と並行                              | ダウンロード後すぐ実行、解析を中断することも | ❌ 保証なし                             | ⚠️ 場合による         | 互いに独立したスクリプト（解析ツール、広告） |
| `<script type="module">` | 並行（`import` 先も含めて）             | `defer` と同じ                               | ✅ 文書順（`async` を付けると保証なし） | ✅ 見える             | モダンな JavaScript（`import` / `export`）   |

#### スコープとクロージャ

- 関数やブロックに入るたびに、エンジンは環境（Environment Record）を作ります。そこには名前と値、そして外側の環境へのリンクがあります。変数はこのチェーンを外へたどって探し、見つからなければ ReferenceError です。
- `var`：関数スコープ。巻き上げられ、`undefined` で初期化される。`let` / `const`：ブロックスコープ。巻き上げられるが一時的デッドゾーン（TDZ）にあり、宣言前にアクセスすると ReferenceError。`const` は再代入できないだけで、オブジェクトの中身は変えられる。
- クロージャが保持するのは変数そのもの（参照）で、作られた時点の値ではありません。だから複数の関数が同じ状態を共有でき、`for (let i…)` が安全なのは、ループのたびに新しい `i` ができるからです。
- プリミティブ型（number、string、boolean、null、undefined、symbol、bigint）は代入時に値がコピーされる。
- オブジェクト（配列、関数、Date、Map を含む）は代入時に参照がコピーされる：二つの変数が同じオブジェクトを指す。
- JS の関数引数は常に「値渡し」ですが、オブジェクト変数の「値」は参照です。これは Java でオブジェクト参照を渡すときと同じ挙動です。

  | 方法                                        | コピーの深さ           | 注意点                                                                                                                                                                 |
  | ------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `{...obj}` / `[...arr]` / `Object.assign()` | 浅いコピー             | 1 階層目だけをコピー。ネストしたオブジェクトや配列は同じ参照を共有したまま。                                                                                           |
  | `structuredClone(x)`                        | 深いコピー             | `Date`、`Map`、`Set`、循環参照に対応。関数・DOM ノード・Vue の `Proxy` はコピーできない（`DataCloneError` が投げられる）。`class` のインスタンスはプロトタイプを失う。 |
  | `JSON.parse(JSON.stringify(x))`             | 深いコピー（欠損あり） | `Date` は文字列になる。`undefined` と関数は消える。`NaN` は `null` になる。循環参照はエラー。                                                                          |

##### this、アロー関数、call / apply / bind

- Java の `this` は常に現在のオブジェクト。JS の `this` は呼び出し時に決まる（アロー関数は例外）。
- `new Foo()`：`this` は新しく作られたオブジェクト。
- `fn.call(obj, …)` / `fn.apply(obj, [args])` / `fn.bind(obj)`：`this` は `obj`。`call` はすぐ実行し引数を一つずつ渡す。`apply` はすぐ実行し引数を配列で渡す。`bind` は `this` を永久に固定した新しい関数を返す。
- `obj.method()`：`this` はドットの左側の `obj`。
- 単なる `fn()`：strict モード（ES module、class 内）では `undefined`、それ以外ではグローバルオブジェクト。
- **アロー関数は自分の `this` を持たず、定義された場所の外側の `this` を使う。call や bind でも変えられない。**

#### イベントループ（Event Loop）

- JS エンジンは一度に一つのコードしか実行しない（シングルスレッド）が、ブラウザがその横でタイマー、ネットワーク、ユーザーイベントなどの機能を提供している。
- イベントループは、「終わった仕事」をメインスレッドに順番に戻し、一つずつ実行するスケジューラ。

1. コールスタック：現在の task の同期コードを、スタックが空になるまで実行する
2. マイクロタスク：`Promise.then`、`await` の後、`queueMicrotask`、`MutationObserver`。すべて空になるまで処理してから次へ進む（処理中に追加されたものも含む）
3. レンダリング（必要なとき）：スタイル計算、レイアウト、描画。`requestAnimationFrame` は描画の前に実行される
4. 次の task：task キューから次を取り出す：`setTimeout` / `setInterval` のコールバック、DOM イベント、`postMessage`、完了したネットワーク通信

- だから `setTimeout(fn, 0)` は「すぐ」ではありません。「少なくとも今回のマイクロタスクと（場合によっては）レンダリングが終わってから、次の task として実行される」という意味です。さらにブラウザには最小遅延があり、5 段階を超えてネストすると最低 4ms に引き上げられ、バックグラウンドタブのタイマーは約 1 秒に 1 回まで間引かれます。
- 長いタスクはページを固まらせる：同期のループがコールスタックを占有している間は、イベント処理もレンダリングもなく、ユーザーには固まって見えます。50ms を超えると long task とみなされます。解決策は処理の分割（メインスレッドを譲る）、Web Worker への移動、アルゴリズムの変更です。
- マイクロタスクの飢餓：マイクロタスクは空になるまで処理され続けるので、各マイクロタスクが新しいマイクロタスクを追加し続けると、task もレンダリングも永遠に回ってきません。
- async/await：`await x` より前のコードは同期的に実行され、後のコードはマイクロタスクになり、`x` が完了してからキューに入ります。async 関数は常に Promise を返します。

#### Promise を深く：状態、チェーン、並行処理、エラーの伝播

- Promise は「まだ分からないが、いずれ結果が出る値」を表す。状態は三つ：pending（待機）→ fulfilled（成功）または rejected（失敗）。
- `.then(onOk, onErr)` は常に新しい Promise を返す。コールバックが return した値が新しい Promise の結果になる（Promise を返した場合はそれに追従する）。コールバックが throw すると新しい Promise は rejected になる。
- エラーの伝播：rejection はチェーンを下って最も近い `catch` / `onErr` を探し、途中の `then(onOk)` はすべて飛ばされる。`catch` が処理して正常に return すれば、チェーンは fulfilled に「回復」する。エラーをさらに下へ伝えたいなら、`catch` の中で再度 throw する。
- Unhandled rejection：rejected の Promise がそのターンの終わりまで誰にも処理されないと、ブラウザは `unhandledrejection` イベントを発火し、Node はデフォルトでプロセスを終了させる。よくある原因：`await` の付け忘れ、内側の Promise の `return` 忘れ、`forEach` の async コールバック内での throw。

| 組み合わせ             | いつ完了するか                         | 失敗時                                                                                        | 用途                                   |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------- |
| `Promise.all()`        | すべて成功したとき                     | **フェイルファスト**：どれか一つでも失敗するとすぐ `reject`（ほかは実行を続けるが結果は無視） | 互いに依存し、一つも欠かせない処理     |
| `Promise.allSettled()` | すべて確定したとき（成功・失敗問わず） | `reject` しない。各結果を `{ status, value \| reason }` で返す                                | バッチ処理、すべての結果を知りたいとき |
| `Promise.race()`       | 最初の一つが確定したとき（成否問わず） | 最初に確定したものが失敗ならすぐ `reject`                                                     | タイムアウト制御、最速の応答を取る     |
| `Promise.any()`        | 最初の一つが成功したとき               | すべて失敗したときだけ `reject`。`AggregateError` を投げる                                    | 複数の予備から最速の成功結果を取る     |

逐次実行と並行実行：ループの中で一つずつ `await` すると、一つ終わってから次を始める（合計時間が足し算になる）。互いに依存しない処理は先に一斉に始めてからまとめて待つ：`await Promise.all(items.map(fn))`。ただし数千件のリクエストを同時に送るとサーバーやブラウザの接続数を食いつぶすので、並行数を制限すること。

- `try/catch` が捕まえられるのは、同期的に投げられたエラーと、`await` した Promise の rejection だけ。`await` していない Promise や、`setTimeout` のコールバック内のエラーは `try/catch` をすり抜ける。
- `fetch` の Promise が reject するのは「ネットワーク層の失敗」（オフライン、DNS 失敗、CORS によるブロック）のときだけで、HTTP 404 / 500 はどちらも fulfilled。`res.ok` は自分で確認する必要がある。これは「2xx 以外ならエラーを投げる」Axios のデフォルトとも、Spring の RestTemplate のデフォルトとも違う。
- Response：`status`、`ok`（200–299）、`headers`。body はストリームなので一度しか読めない（`res.json()` か `res.text()` のどちらか一方。二回読むなら `res.clone()`）。`res.json()` 自体も Promise で、中身が正しい JSON でなければ `SyntaxError` で reject する。
- AbortController：`const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal }); ctrl.abort()`。中断された fetch は `AbortError`（`DOMException`、`e.name === "AbortError"`）で reject する。これは「正常なキャンセル」でありエラーではないので、エラーメッセージは表示しないこと。controller は一度 abort すると再利用できないので、リクエストごとに新しく作る。
- タイムアウト：`fetch(url, { signal: AbortSignal.timeout(5000) })` はタイムアウト時に `TimeoutError` で reject する。「手動キャンセル + タイムアウト」を併用するなら `AbortSignal.any([ctrl.signal, AbortSignal.timeout(5000)])`。fetch にはデフォルトのタイムアウトがなく、永遠に待ち続けることがある。
- CORS：クロスオリジンのリクエストはブラウザが強制的にチェックする。サーバーが正しい `Access-Control-Allow-Origin` を返さないと、fetch は `TypeError: Failed to fetch` で reject し、JS からは原因が見えない。「シンプルリクエスト」でないもの（例：`Authorization` 付きや JSON の content-type）は、先に OPTIONS のプリフライトが送られる。解決するのはサーバー側（Spring：`@CrossOrigin` か `CorsRegistry`）で、フロントではない。
- 競合状態（race condition）：ユーザーが "a" と入力し、続けて "ab" と入力する。二つのリクエストの応答順は保証されない。"a" の応答が遅れて後から届くと "ab" の結果を上書きし、画面に古いデータが表示される。解決策：新しいリクエストを出すときに前のものを中断する（AbortController）か、リクエストに連番を付けて最新のものだけを受け入れる。


- (A) 1 2 3 4 5
- (B) 1 5 3 4 2
- (C) 1 5 2 3 4
- (D) 1 5 4 3 2

<details>
<summary>答えを見る</summary>

**(B) 1 5 3 4 2**

まず同期コードが実行される（1、5）。次にマイクロタスクキューを空にする。`then` と `queueMicrotask` は同じキューに入り、先に入ったものから実行される（3、4）。`setTimeout` は次の task なので最後（2）。

</details>

**Q2. 出力の順番は？**

```javascript
async function f() {
  console.log("1");
  await null;
  console.log("2");
}
console.log("3");
f();
console.log("4");
```

- (A) 3 1 2 4
- (B) 3 4 1 2
- (C) 3 1 4 2
- (D) 1 2 3 4

<details>
<summary>答えを見る</summary>

**(C) 3 1 4 2**

async 関数を呼ぶと、`await` より前のコードは同期的に実行されるので、1 は 3 のすぐ後。`await` より後のコードはマイクロタスクになり、今の同期コード（4 を出力）が終わってから実行される。

</details>

**Q3. 出力の順番は？**

```javascript
new Promise(resolve => {
  console.log("x");
  resolve();
  console.log("y");
}).then(() => console.log("z"));
console.log("w");
```

- (A) x y w z
- (B) x z y w
- (C) w x y z
- (D) x w y z

<details>
<summary>答えを見る</summary>

**(A) x y w z**

`new Promise` の executor は**同期的に**実行され、`resolve()` で中断されることもないので、y もそのまま出力される。`then` のコールバックはマイクロタスクなので、同期の w が出力されてから z の番になる。

</details>

**Q4. 二つの Promise チェーンが交差するとき、出力の順番は？**

```javascript
Promise.resolve()
  .then(() => console.log("a1"))
  .then(() => console.log("a2"));
Promise.resolve()
  .then(() => console.log("b1"))
  .then(() => console.log("b2"));
```

- (A) a1 a2 b1 b2
- (B) a1 b1 a2 b2
- (C) b1 b2 a1 a2
- (D) 順番は決まっていない

<details>
<summary>答えを見る</summary>

**(B) a1 b1 a2 b2**

各 `.then` は、前の Promise が確定してから次のコールバックをマイクロタスクキューに入れる。そのため最初のラウンドでキューにあるのは a1 と b1 だけで、それらを実行したことで a2 と b2 がキューに入る。順番は決まっていて、ランダムではない。

</details>

**Q5. 出力の順番は？**

```javascript
setTimeout(() => {
  console.log("t1");
  Promise.resolve().then(() => console.log("p1"));
}, 0);
setTimeout(() => console.log("t2"), 0);
```

- (A) t1 t2 p1
- (B) p1 t1 t2
- (C) t1 p1 t2
- (D) t2 t1 p1

<details>
<summary>答えを見る</summary>

**(C) t1 p1 t2**

イベントループは task を一つ実行するたびに、次の task を取る前にマイクロタスクを空にする。t1 の task の中でキューに入った p1 は、t2 より先に実行される。

</details>

**Q6. 出力は？**

```javascript
Promise.reject(new Error("boom"))
  .then(() => console.log("A"))
  .catch(() => {
    console.log("B");
    return 1;
  })
  .then(v => console.log("C", v));
```

- (A) A B C 1
- (B) B
- (C) B C 1
- (D) B C undefined

<details>
<summary>答えを見る</summary>

**(C) B C 1**

rejection は途中の `then(onOk)` を飛ばして最も近い `catch` へ直行するので、A は出力されない。`catch` が正常に `return 1` すると、チェーンは fulfilled に回復し、次の `then` は 1 を受け取る。

</details>

**Q7. `p1` は 100ms 後に成功、`p2` は 50ms 後に失敗する。`Promise.all([p1, p2])` はどうなる？**

- (A) 100ms 後に fulfilled、結果は `[p1 の値, undefined]`
- (B) 約 50ms で p2 のエラーにより rejected。p1 は実行を続ける
- (C) 約 50ms で rejected。p1 はキャンセルされる
- (D) 100ms 後に rejected

<details>
<summary>答えを見る</summary>

**(B)**

`Promise.all` はフェイルファスト：どれか一つが失敗するとすぐ reject する。ただし Promise には「キャンセル」の仕組みがないので、p1 は最後まで実行され、結果が無視されるだけ。失敗も含めてすべての結果が必要なら `Promise.allSettled` を使う。

</details>

#### 二、スコープ、巻き上げ、クロージャ

**Q8. 出力は？**

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

- (A) 0 1 2
- (B) 3 3 3
- (C) 2 2 2
- (D) undefined ×3

<details>
<summary>答えを見る</summary>

**(B) 3 3 3**

`var` は関数スコープなので、三つのコールバックは同じ `i` を共有する。クロージャが保持するのは変数そのもので、その時点の値ではない。コールバックが実行されるころにはループは終わっていて、`i` は 3 になっている。`let` にすれば 0 1 2 と出力される。ループのたびに新しい `i` ができるからだ。

</details>

**Q9. 実行するとどうなる？**

```javascript
console.log(a);
console.log(b);
var a = 1;
let b = 2;
```

- (A) 1 を出力し、次に 2 を出力
- (B) undefined を出力し、次に undefined を出力
- (C) undefined を出力し、その後 ReferenceError
- (D) 1 行目で ReferenceError

<details>
<summary>答えを見る</summary>

**(C)**

`var a` は巻き上げられて `undefined` で初期化されるので、1 行目は undefined を出力する。`let b` も巻き上げられるが、宣言までは一時的デッドゾーン（TDZ）にあり、アクセスすると ReferenceError になる。

</details>

**Q10. どの行でエラーになる？**

```javascript
const o = { n: 1 };
o.n = 2; // 2 行目
o.m = 3; // 3 行目
o = { n: 4 }; // 4 行目
```

- (A) 2 行目
- (B) 3 行目
- (C) 4 行目
- (D) どれもエラーにならない

<details>
<summary>答えを見る</summary>

**(C) 4 行目**。`TypeError: Assignment to constant variable.` が投げられる。

`const` が禁じるのは「再代入」だけで、オブジェクトの中身を変えたりプロパティを追加したりはできる。Java の `final` 参照と同じ考え方だ。

</details>

#### 三、this と call / apply / bind

**Q11. strict モードでの結果は？**

```javascript
"use strict";
const obj = {
  name: "obj",
  hi() {
    return this.name;
  },
};
const f = obj.hi;
console.log(obj.hi());
console.log(f());
```

- (A) obj、obj
- (B) obj、undefined
- (C) obj の後、TypeError
- (D) undefined、undefined

<details>
<summary>答えを見る</summary>

**(C)**

`this` は呼び出し時に決まる。`obj.hi()` ではドットの左が obj なので、`this` は obj。メソッドを取り出して `f()` と単独で呼ぶと、strict モードでは `this` は `undefined` になり、`undefined.name` を読もうとして TypeError になる。メソッドをコールバックとして渡すとき（例：`button.addEventListener("click", obj.hi)`）によくハマる落とし穴だ。

</details>

**Q12. ES module の中での出力は？**

```javascript
const obj = {
  name: "obj",
  regular() {
    return this.name;
  },
  arrow: () => this,
};
console.log(obj.regular(), obj.arrow());
```

- (A) obj obj
- (B) obj undefined
- (C) obj window
- (D) undefined undefined

<details>
<summary>答えを見る</summary>

**(B) obj undefined**

アロー関数は自分の `this` を持たず、**定義された**場所の外側の `this` を使う。ここで外側は module のトップレベルで、`this` は `undefined`。オブジェクトリテラルの波かっこは新しい `this` を作らないので、アロー関数をオブジェクトのメソッドにしてはいけない。

</details>

**Q13. 出力は？**

```javascript
function f() {
  return this.n;
}
const g = f.bind({ n: 1 });
console.log(g.call({ n: 2 }));
```

- (A) 1
- (B) 2
- (C) undefined
- (D) TypeError

<details>
<summary>答えを見る</summary>

**(A) 1**

`bind` が返す新しい関数は `this` が永久に固定されていて、後から `call` や `apply` を使っても変えられない。

</details>

**Q14. call、apply、bind について正しいのはどれ？**

- (A) 三つとも関数をすぐに実行する
- (B) `apply` はすぐに実行し、引数を配列で渡す
- (C) `bind` はすぐに実行し、`this` を永久に固定する
- (D) `call` は新しい関数を返し、引数を一つずつ渡す

<details>
<summary>答えを見る</summary>

**(B)**

- `call`：すぐ実行、引数は一つずつ：`fn.call(obj, a, b)`
- `apply`：すぐ実行、引数は配列：`fn.apply(obj, [a, b])`
- `bind`：実行しない。`this` を固定した新しい関数を返す

</details>

#### 四、型、比較、コピー

**Q15. 結果が `true` になるのはどれ？**

- (A) `NaN === NaN`
- (B) `null === undefined`
- (C) `"0" === 0`
- (D) `null == undefined`

<details>
<summary>答えを見る</summary>

**(D)**

`==` は先に型変換を行い、`null == undefined` は仕様で特別に true と定められている。`===` は型変換しないので、(B)(C) はどちらも false。`NaN` は自分自身も含めて何とも等しくならない。NaN の判定には `Number.isNaN()` を使う。

</details>

**Q16. 何が出力される？**

```javascript
const a = { x: 1, inner: { y: 1 } };
const b = { ...a };
b.x = 2;
b.inner.y = 2;
console.log(a.x, a.inner.y);
```

- (A) 1 1
- (B) 2 2
- (C) 1 2
- (D) 2 1

<details>
<summary>答えを見る</summary>

**(C) 1 2**

スプレッド構文は浅いコピー。1 階層目の `x` はコピーされるので、`b.x` を変えても `a` には影響しない。しかし `inner` は参照がコピーされるので、両方が同じオブジェクトを指している。深いコピーが必要なら `structuredClone(a)` を使う。

</details>

**Q17. `JSON.parse(JSON.stringify({ d: new Date(0), u: undefined, n: NaN }))` の結果は？**

- (A) `{ d: Date オブジェクト, u: undefined, n: NaN }`
- (B) `{ d: "1970-01-01T00:00:00.000Z", n: null }`
- (C) `{ d: "1970-01-01T00:00:00.000Z", u: null, n: NaN }`
- (D) エラーになる

<details>
<summary>答えを見る</summary>

**(B)**

JSON による深いコピーは欠損がある：`Date` は ISO 文字列になり、値が `undefined` のプロパティは消え、`NaN` は `null` になる。

</details>

**Q18. 結果は？**

```javascript
localStorage.setItem("user", { name: "Clark" });
console.log(localStorage.getItem("user"));
```

- (A) `{ name: "Clark" }`
- (B) `'{"name":"Clark"}'`
- (C) `"[object Object]"`
- (D) TypeError

<details>
<summary>答えを見る</summary>

**(C) `"[object Object]"`**

localStorage は文字列しか保存できない。オブジェクトを渡すと `String()` で `"[object Object]"` に変換され、エラーも出ないまま、データが静かに壊れる。オブジェクトを保存するなら、先に `JSON.stringify` し、読み出すときに `JSON.parse` する。

</details>

#### 五、ブラウザ API とエラー処理

**Q19. 結果は？**

```javascript
try {
  setTimeout(() => {
    throw new Error("x");
  }, 0);
} catch (e) {
  console.log("caught");
}
```

- (A) caught を出力
- (B) 何も出力されず、Console に Uncaught Error: x
- (C) 何も出力されず、エラーは静かに握りつぶされる
- (D) caught を出力した後、Uncaught Error

<details>
<summary>答えを見る</summary>

**(B)**

`try` ブロックはタイマーを「予約」しただけで終わる。コールバックが後で別の task として実行されるとき、元の try/catch はもうコールスタック上になく、エラーを捕まえられない。捕まえたいなら、try/catch をコールバックの中に書くか、Promise と `await` に切り替える。

</details>

**Q20. `fetch("/api/not-found")` が HTTP 404 を受け取ったら、どうなる？**

- (A) Promise は rejected、TypeError が投げられる
- (B) Promise は rejected、HTTP 404 エラーが投げられる
- (C) Promise は fulfilled、`res.ok` は false、`res.status` は 404
- (D) Promise は永遠に pending のまま

<details>
<summary>答えを見る</summary>

**(C)**

fetch が reject するのは、ネットワーク層の失敗（オフライン、DNS 失敗、CORS によるブロック）のときだけ。サーバーが応答さえすれば、404 や 500 でも fulfilled になり、`res.ok` は自分で確認する必要がある。「2xx 以外ならエラーを投げる」Axios のデフォルトとはここが違う。

</details>
