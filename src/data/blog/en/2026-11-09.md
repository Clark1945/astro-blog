### HTML

The language you write pages in. My conclusion: you don't need to study it. Look at a few web pages and you'll get it.

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Page title</title>
    <link rel="stylesheet" href="css/style.css" />
  </head>
  <body>
    <h1>Heading</h1>
    <p>
      A paragraph with a
      <a href="https://developer.mozilla.org/en-US/">link</a> in it.
    </p>
    <script defer src="js/app.js"></script>
  </body>
</html>
```

Attributes: id, class, data-\*

```html
<article class="event major" id="tw-1895-cession" data-year="1895"></article>
```

- id: unique on the page, used to locate an element; it's also the `#id` anchor in a URL.
- class: an element can have several, and they can repeat; used for styling and selecting elements.

### CSS

HTML is the skeleton; CSS decorates it.
There are three ways to include it:

- An external file (`<link rel=...>`, recommended)
- A `<style>` block
- A `style="..."` attribute on the element (only for quick debugging)

When several rules set the same property, the one with higher specificity wins: inline style beats `#id`, which beats `.class`, attributes and pseudo-classes, which beat tag names. At the same level, the rule written later wins. `!important` overrides everything, but it makes the code hard to maintain later, so avoid it.

#### Async and browser APIs

JS runs on a single thread. Anything that has to wait, like a network request or a timer, is handed to the browser; when it's done, its callback is queued and only runs after the current code finishes. That's why the page doesn't freeze while waiting, but you have to pay attention to "what runs first".

```javascript
<script>
console.log("1");
setTimeout(() => console.log("4"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("2");
// runs in the order 1 2 3 4
</script>
```

Promise and async/await

```javascript
async function loadJson(url) {
  const res = await fetch(url); // waits for the network without freezing the page
  if (!res.ok) throw new Error("HTTP " + res.status); // fetch does not throw on 404 by itself
  return res.json(); // also a Promise
}

async function main() {
  try {
    const data = await loadJson("/data/taiwan.json");
    console.log(data.events.length);
  } catch (err) {
    console.error("Failed to load", err);
  }
}
main();
```

**localStorage** can only store strings; objects need `JSON.stringify` first. It persists within the same site and browser, but it is not secure storage, so never put passwords or tokens in it.

```javascript
try {
  localStorage.setItem("theme", "dark");
  const theme = localStorage.getItem("theme"); // null if not set
} catch (e) {
  // throws in private mode or when disabled; the page must still work
}
```

#### HTML Constraint Validation

| Attribute                         | Effect                                                  | Notes                                                                                                          |
| --------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `required`                        | Cannot be left empty.                                   | The form won't submit if the user leaves it blank.                                                             |
| `type="email"`                    | Checks for a valid email format.                        | Phones show a keyboard suited to typing email addresses.                                                       |
| `type="url"`                      | Checks for a valid URL format.                          | Usually needs a scheme such as `https://`.                                                                     |
| `type="number"`                   | Numbers only.                                           | Not for phone numbers, postal codes or ID numbers: a leading `0` may be lost.                                  |
| `type="date"`                     | Shows a date picker and validates the date format.      | The value is handled in a standard date format.                                                                |
| `type="text" inputmode="numeric"` | A text field, but phones show a numeric keypad.         | Good for phone numbers, postal codes and ID numbers that need to keep a leading `0`.                           |
| `pattern`                         | Validates the input against a regular expression.       | Must match the whole string (an implicit `^(?:…)$`); text-type inputs only; add a `title` explaining the rule. |
| `min` / `max` / `step`            | Minimum, maximum and step for numbers, dates or ranges. | Mainly for `number`, `date` and `range`.                                                                       |
| `minlength`                       | Minimum number of characters.                           | Common for usernames and passwords.                                                                            |
| `maxlength`                       | Maximum number of characters.                           | The user can't type past the limit.                                                                            |

- Front-end vs back-end validation: front-end validation is for user experience (instant feedback, one fewer round trip); back-end validation is the security boundary, because anyone can bypass the front end with curl. Do both. In Spring Boot, use `@Valid` with Bean Validation (`@NotBlank`, `@Email`, `@Size`) and return 400 with field errors; the front end maps those errors back to the fields. The two sets of rules will drift apart, and the back end is the source of truth.
- Preventing double submission: in the submit handler, disable the submit button and guard with a flag (Enter and the button go through the same path). The back end must also be idempotent (an idempotency key or a unique key), because users can still refresh, double-click, or have the network retry.
- For sign-up, checkout and admin CRUD forms, attributes cover most rules (required, format, length). Use `setCustomValidity` only for complex cross-field rules (password confirmation, start and end dates).
- Use `form.requestSubmit()` instead of `form.submit()`: the former runs validation and fires the submit event; the latter skips both.

#### Resource loading

The HTML parser works as a stream: it downloads and parses at the same time. What it does when it meets a `<script>` depends on the script's attributes. Picking the wrong one can cost you anything from a slow page to `querySelector` returning `null`.

| Loading                  | Download                               | When it runs                                           | Order of multiple scripts                       | Sees the DOM after it | Use for                                 |
| ------------------------ | -------------------------------------- | ------------------------------------------------------ | ----------------------------------------------- | --------------------- | --------------------------------------- |
| Plain `<script>`         | Immediately, pausing HTML parsing      | Right after download, blocking parsing                 | Document order                                  | ❌ No                 | Almost never                            |
| `<script defer>`         | In parallel with parsing               | After HTML parsing finishes, before `DOMContentLoaded` | ✅ Document order                               | ✅ Yes                | Your application's main code            |
| `<script async>`         | In parallel with parsing               | Right after download, possibly interrupting parsing    | ❌ Not guaranteed                               | ⚠️ Not always         | Independent scripts (analytics, ads)    |
| `<script type="module">` | In parallel (along with its `import`s) | Same as `defer`                                        | ✅ Document order (not guaranteed with `async`) | ✅ Yes                | Modern JavaScript (`import` / `export`) |

#### Scope and closures

- Each time you enter a function or block, the engine creates an environment (Environment Record) holding names and values, plus a link to the outer environment. Variable lookup walks outward along this chain; if nothing is found, you get a ReferenceError.
- `var`: function-scoped, hoisted and initialized to `undefined`. `let` / `const`: block-scoped, hoisted but in the temporal dead zone (TDZ), so accessing them before the declaration throws a ReferenceError. `const` only forbids reassignment; an object's contents can still change.
- A closure keeps the variable itself (a reference), not its value at the time it was created. That's how several functions can share the same state, and why `for (let i…)` is safe: every iteration gets its own new `i`.
- Primitives (number, string, boolean, null, undefined, symbol, bigint) are copied by value on assignment.
- Objects (including arrays, functions, Date, Map) copy the reference on assignment: both variables point to the same object.
- JS function arguments are always "passed by value", but the "value" of an object variable is a reference, which is the same behavior as passing object references in Java.

  | Approach                                    | Copy depth   | Notes                                                                                                                                                                      |
  | ------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `{...obj}` / `[...arr]` / `Object.assign()` | Shallow      | Copies only the first level; nested objects and arrays still share the same reference.                                                                                     |
  | `structuredClone(x)`                        | Deep         | Supports `Date`, `Map`, `Set` and circular references; can't copy functions, DOM nodes or Vue's `Proxy` (throws `DataCloneError`); `class` instances lose their prototype. |
  | `JSON.parse(JSON.stringify(x))`             | Deep (lossy) | `Date` becomes a string; `undefined` and functions disappear; `NaN` becomes `null`; circular references throw.                                                             |

##### this, arrow functions, call / apply / bind

- In Java, `this` is always the current object. In JS, `this` is decided at call time (arrow functions are the exception).
- `new Foo()`: `this` is the newly created object.
- `fn.call(obj, …)` / `fn.apply(obj, [args])` / `fn.bind(obj)`: `this` is `obj`. `call` runs immediately with arguments passed one by one; `apply` runs immediately with arguments in an array; `bind` returns a new function with `this` bound permanently.
- `obj.method()`: `this` is the `obj` to the left of the dot.
- A plain `fn()`: `undefined` in strict mode (ES modules, inside classes), otherwise the global object.
- **Arrow functions have no `this` of their own. They use the `this` of the enclosing scope where they were defined, and neither call nor bind can change it.**

#### The Event Loop

- The JS engine runs one piece of code at a time (single-threaded), but the browser provides timers, networking, user events and so on alongside it.
- The event loop is the scheduler that queues "finished work" back onto the main thread and runs it one item at a time.

1. Call stack: run the synchronous code of the current task until the stack is empty
2. Microtasks: `Promise.then`, code after `await`, `queueMicrotask`, `MutationObserver`. The queue is drained completely before moving on (including microtasks added while draining)
3. Render, when needed: style calculation, layout, paint; `requestAnimationFrame` runs before paint
4. Next task: take the next item from the task queue: `setTimeout` / `setInterval` callbacks, DOM events, `postMessage`, completed network requests

- So `setTimeout(fn, 0)` is not "immediately". It means "at least after this round's microtasks and (possibly) rendering, as the next task". Browsers also enforce a minimum delay: past 5 levels of nesting it's clamped to at least 4ms, and timers in background tabs are throttled to about once per second.
- Long tasks freeze the page: a synchronous loop holds the call stack, so there's no event handling and no rendering in the meantime, and the user sees a frozen page. Anything over 50ms counts as a long task. Fixes: split the work into chunks (yield to the main thread), move it to a Web Worker, or change the algorithm.
- Microtask starvation: the microtask queue is always drained until empty. If every microtask queues another microtask, tasks and rendering never get a turn.
- async/await: code before `await x` runs synchronously; code after it becomes a microtask that is queued once `x` settles. An async function always returns a Promise.

#### Promises in depth: state, chaining, concurrency and error propagation

- A Promise represents "a value that isn't known yet but will have a result later". Three states: pending → fulfilled (success) or rejected (failure).
- `.then(onOk, onErr)` always returns a new Promise. The value the callback returns becomes the new Promise's result (a returned Promise is adopted); if the callback throws, the new Promise is rejected.
- Error propagation: a rejection travels down the chain to the nearest `catch` / `onErr`, skipping every `then(onOk)` on the way. Once a `catch` handles it and returns normally, the chain "recovers" to fulfilled. To keep the error going, rethrow it inside the `catch`.
- Unhandled rejection: if a rejected Promise has no handler by the end of the round, the browser fires an `unhandledrejection` event, and Node terminates the process by default. Common causes: a missing `await`, forgetting to `return` an inner Promise, throwing inside an async callback passed to `forEach`.

| Combinator             | Settles when                       | On failure                                                                                      | Use for                                         |
| ---------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `Promise.all()`        | All succeed                        | **Fails fast**: rejects as soon as any Promise fails (the others keep running, results ignored) | Tasks that depend on each other; all are needed |
| `Promise.allSettled()` | All settle (fulfilled or rejected) | Never rejects; returns `{ status, value \| reason }` for each                                   | Batch jobs where you need every result          |
| `Promise.race()`       | The first one settles (either way) | Rejects immediately if the first to settle fails                                                | Timeouts, taking the fastest response           |
| `Promise.any()`        | The first one succeeds             | Rejects only if all fail, with an `AggregateError`                                              | The fastest success among several fallbacks     |

Sequential vs concurrent: awaiting each item inside a loop runs them one after another (the times add up). Independent work should be started together and awaited together: `await Promise.all(items.map(fn))`. But firing thousands of requests at once will overwhelm the server or the browser's connection limit, so cap the concurrency.

- `try/catch` only catches errors thrown synchronously and rejections of Promises you `await`. A Promise you don't await, and errors inside a `setTimeout` callback, both escape the `try/catch`.
- A `fetch` Promise rejects only on network-level failure (offline, DNS failure, blocked by CORS). HTTP 404 / 500 are both fulfilled, so you must check `res.ok` yourself. This differs from Axios, which throws on non-2xx by default, and from Spring's RestTemplate defaults.
- Response: `status`, `ok` (200–299), `headers`. The body is a stream and can be read only once (pick one of `res.json()` or `res.text()`; to read it twice, use `res.clone()`). `res.json()` is itself a Promise and rejects with a `SyntaxError` if the content isn't valid JSON.
- AbortController: `const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal }); ctrl.abort()`. An aborted fetch rejects with an `AbortError` (a `DOMException`, `e.name === "AbortError"`). That's a normal cancellation, not an error, so don't show an error message. A controller can't be reused once aborted; create a new one for each request.
- Timeouts: `fetch(url, { signal: AbortSignal.timeout(5000) })` rejects with a `TimeoutError` on timeout. To combine manual cancellation with a timeout: `AbortSignal.any([ctrl.signal, AbortSignal.timeout(5000)])`. fetch has no timeout by default and can wait forever.
- CORS: the browser enforces checks on cross-origin requests. If the server doesn't send the right `Access-Control-Allow-Origin`, fetch rejects with `TypeError: Failed to fetch`, and JS can't see why. Requests that aren't "simple" (for example with `Authorization` or a JSON content type) send an OPTIONS preflight first. The fix belongs on the server (Spring: `@CrossOrigin` or `CorsRegistry`), not the front end.
- Race conditions: the user types "a", then "ab". The two responses can arrive in any order. If the response for "a" is slower and arrives last, it overwrites the result for "ab", and the page shows stale data. Fixes: abort the previous request when a new one starts (AbortController), or tag requests with a sequence number and accept only the latest.

#### 1. Event loop and Promises

**Q1. What is the output order?**

```javascript
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
queueMicrotask(() => console.log("4"));
console.log("5");
```

- (A) 1 2 3 4 5
- (B) 1 5 3 4 2
- (C) 1 5 2 3 4
- (D) 1 5 4 3 2

<details>
<summary>Show answer</summary>

**(B) 1 5 3 4 2**

The synchronous code runs first (1, 5). Then the microtask queue is drained: `then` and `queueMicrotask` go into the same queue, first in, first out (3, 4). `setTimeout` is the next task, so it comes last (2).

</details>

**Q2. What is the output order?**

```javascript
async function f() {
  console.log("1");
  await null;
  console.log("2");
}
console.log("3");
f();
console.log("4");
```

- (A) 3 1 2 4
- (B) 3 4 1 2
- (C) 3 1 4 2
- (D) 1 2 3 4

<details>
<summary>Show answer</summary>

**(C) 3 1 4 2**

When you call an async function, the code before `await` runs synchronously, so 1 comes right after 3. The code after `await` becomes a microtask and runs only after the current synchronous code (which prints 4) finishes.

</details>

**Q3. What is the output order?**

```javascript
new Promise(resolve => {
  console.log("x");
  resolve();
  console.log("y");
}).then(() => console.log("z"));
console.log("w");
```

- (A) x y w z
- (B) x z y w
- (C) w x y z
- (D) x w y z

<details>
<summary>Show answer</summary>

**(A) x y w z**

The executor of `new Promise` runs **synchronously**, and `resolve()` doesn't stop it, so y still prints. The `then` callback is a microtask, so z waits until the synchronous w has printed.

</details>

**Q4. Two Promise chains interleave. What is the output order?**

```javascript
Promise.resolve()
  .then(() => console.log("a1"))
  .then(() => console.log("a2"));
Promise.resolve()
  .then(() => console.log("b1"))
  .then(() => console.log("b2"));
```

- (A) a1 a2 b1 b2
- (B) a1 b1 a2 b2
- (C) b1 b2 a1 a2
- (D) The order isn't fixed

<details>
<summary>Show answer</summary>

**(B) a1 b1 a2 b2**

Each `.then` queues its callback only after the previous Promise settles. So in the first round only a1 and b1 are in the queue; running them is what queues a2 and b2. The order is deterministic, not random.

</details>

**Q5. What is the output order?**

```javascript
setTimeout(() => {
  console.log("t1");
  Promise.resolve().then(() => console.log("p1"));
}, 0);
setTimeout(() => console.log("t2"), 0);
```

- (A) t1 t2 p1
- (B) p1 t1 t2
- (C) t1 p1 t2
- (D) t2 t1 p1

<details>
<summary>Show answer</summary>

**(C) t1 p1 t2**

After each task, the event loop drains the microtask queue before taking the next task. p1, queued inside the t1 task, runs before t2.

</details>

**Q6. What is the output?**

```javascript
Promise.reject(new Error("boom"))
  .then(() => console.log("A"))
  .catch(() => {
    console.log("B");
    return 1;
  })
  .then(v => console.log("C", v));
```

- (A) A B C 1
- (B) B
- (C) B C 1
- (D) B C undefined

<details>
<summary>Show answer</summary>

**(C) B C 1**

A rejection skips every `then(onOk)` on the way and goes straight to the nearest `catch`, so A never prints. After the `catch` returns 1 normally, the chain recovers to fulfilled, and the next `then` receives 1.

</details>

**Q7. `p1` succeeds after 100ms; `p2` fails after 50ms. What does `Promise.all([p1, p2])` do?**

- (A) Fulfills after 100ms with `[p1's value, undefined]`
- (B) Rejects at about 50ms with p2's error; p1 keeps running
- (C) Rejects at about 50ms, and p1 is cancelled
- (D) Rejects after 100ms

<details>
<summary>Show answer</summary>

**(B)**

`Promise.all` fails fast: it rejects as soon as any one fails. But Promises have no "cancel" mechanism, so p1 runs to completion and its result is ignored. If you need every result (including failures), use `Promise.allSettled`.

</details>

#### 2. Scope, hoisting and closures

**Q8. What is the output?**

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

- (A) 0 1 2
- (B) 3 3 3
- (C) 2 2 2
- (D) undefined ×3

<details>
<summary>Show answer</summary>

**(B) 3 3 3**

`var` is function-scoped, so all three callbacks share the same `i`. A closure keeps the variable itself, not its value at that moment; by the time the callbacks run, the loop has finished and `i` is 3. With `let` it prints 0 1 2, because every iteration gets its own new `i`.

</details>

**Q9. What happens when this runs?**

```javascript
console.log(a);
console.log(b);
```

</details>

#### 3. this and call / apply / bind

**Q11. In strict mode, what is the result?**

```javascript
"use strict";
const obj = {
  name: "obj",
  hi() {
    return this.name;
  },
};
const f = obj.hi;
console.log(obj.hi());
console.log(f());
```

- (A) obj, obj
- (B) obj, undefined
- (C) obj, then a TypeError
- (D) undefined, undefined

<details>
<summary>Show answer</summary>

**(C)**

`this` is decided at call time. In `obj.hi()`, the thing left of the dot is obj, so `this` is obj. Pulled out and called on its own as `f()`, `this` is `undefined` in strict mode, and reading `undefined.name` throws a TypeError. You hit this when passing a method as a callback, e.g. `button.addEventListener("click", obj.hi)`.

</details>

**Q12. In an ES module, what is the output?**

```javascript
const obj = {
  name: "obj",
  regular() {
    return this.name;
  },
  arrow: () => this,
};
console.log(obj.regular(), obj.arrow());
```

- (A) obj obj
- (B) obj undefined
- (C) obj window
- (D) undefined undefined

<details>
<summary>Show answer</summary>

**(B) obj undefined**

Arrow functions have no `this` of their own; they use the `this` of the scope where they were **defined**. Here that's the top level of the module, where `this` is `undefined`. An object literal's braces don't create a new `this`, so don't use arrow functions as object methods.

</details>

**Q13. What is the output?**

```javascript
function f() {
```

- (B) 2
- (C) undefined

**Q14. Which statement about call, apply and bind is correct?**

- (A) All three call the function immediately
- (B) `apply` calls it immediately, with arguments passed as an array
- (C) `bind` calls it immediately and binds `this` permanently
- (D) `call` returns a new function, with arguments passed one by one

**(B)**

#### 4. Types, comparison and copying

**Q15. Which expression evaluates to `true`?**

- (A) `NaN === NaN`
- (B) `null === undefined`
- (C) `"0" === 0`
- (D) `null == undefined`

<details>
<summary>Show answer</summary>

**(D)**

`==` converts types first, and the spec specifically defines `null == undefined` as true. `===` doesn't convert, so (B) and (C) are false. `NaN` isn't equal to anything, including itself; use `Number.isNaN()` to check for it.

</details>

**Q16. What does this print?**

```javascript
const a = { x: 1, inner: { y: 1 } };
const b = { ...a };
b.x = 2;
b.inner.y = 2;
console.log(a.x, a.inner.y);
```

- (A) 1 1
- (B) 2 2
- (C) 1 2
- (D) 2 1

<details>
<summary>Show answer</summary>

**(C) 1 2**

The spread operator makes a shallow copy: the first-level `x` is copied, so changing `b.x` doesn't affect `a`. But `inner` is copied as a reference, so both point to the same object. For a deep copy, use `structuredClone(a)`.

</details>

**Q17. What is the result of `JSON.parse(JSON.stringify({ d: new Date(0), u: undefined, n: NaN }))`?**

- (A) `{ d: a Date object, u: undefined, n: NaN }`
- (B) `{ d: "1970-01-01T00:00:00.000Z", n: null }`
- (C) `{ d: "1970-01-01T00:00:00.000Z", u: null, n: NaN }`
- (D) Throws an error

<details>
<summary>Show answer</summary>

**(B)**

A JSON deep copy is lossy: `Date` becomes an ISO string, properties whose value is `undefined` disappear, and `NaN` becomes `null`.

</details>

**Q18. What is the result?**

```javascript
localStorage.setItem("user", { name: "Clark" });
console.log(localStorage.getItem("user"));
```

- (A) `{ name: "Clark" }`
- (B) `'{"name":"Clark"}'`
- (C) `"[object Object]"`
- (D) Throws a TypeError

<details>
<summary>Show answer</summary>

**(C) `"[object Object]"`**

localStorage stores only strings. An object passed in is converted with `String()` into `"[object Object]"`, with no error, so the data is silently corrupted. To store an object, `JSON.stringify` it first and `JSON.parse` it when reading.

</details>

#### 5. Browser APIs and error handling

**Q19. What is the result?**

```javascript
try {
  setTimeout(() => {
    throw new Error("x");
  }, 0);
} catch (e) {
  console.log("caught");
}
```

- (A) Prints caught
- (B) Prints nothing; the Console shows Uncaught Error: x
- (C) Prints nothing; the error is silently swallowed
- (D) Prints caught, then shows Uncaught Error

<details>
<summary>Show answer</summary>

**(B)**

The `try` block only schedules a timer and then ends. When the callback runs later, in a different task, the original try/catch is no longer on the call stack and can't catch it. To catch the error, put the try/catch inside the callback, or switch to a Promise with `await`.

</details>

**Q20. `fetch("/api/not-found")` gets an HTTP 404. What happens?**

- (A) The Promise rejects with a TypeError
- (B) The Promise rejects with an HTTP 404 error
- (C) The Promise fulfills; `res.ok` is false and `res.status` is 404
- (D) The Promise stays pending forever

<details>
<summary>Show answer</summary>

**(C)**

fetch rejects only on network-level failure (offline, DNS failure, blocked by CORS). As long as the server responds, including with 404 or 500, the Promise fulfills, and you must check `res.ok` yourself. This differs from Axios, which throws on non-2xx by default.

</details>
